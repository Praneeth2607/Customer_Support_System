### Decision 1: Chunked Streaming for Dataset Audit & Ingestion
* **Context**: The raw dataset `twcs.csv` is ~492.6 MB and contains 2,811,774 rows. Naively loading the entire CSV into pandas memory creates multi-gigabyte memory spikes and risk of process thrashing, especially on developer machines.
* **Decision**: Implemented chunked generator streaming (`chunksize=200_000`) for all full-dataset scans and brand filtering.
* **Why**: Streaming bounds RAM usage to <300MB, allows progress reporting, and runs in ~36 seconds while preventing out-of-memory errors on arbitrary hardware.
* **Alternatives Considered**: 
  - *Full `pd.read_csv`*: Rejected due to high peak RAM consumption (~2.5 GB) and unsuitability for constrained environments.
  - *SQLite/DuckDB database ingestion*: Considered, but adding external database dependencies for a 1-time extraction phase was deemed premature complexity when chunked pandas satisfies the 36-second requirement with zero extra overhead.

### Decision 2: Brand Handle Verification (`Uber_Support`)
* **Context**: We hypothesized focusing on Uber based on volume, but Twitter datasets often feature multiple sub-handles (e.g., `@Uber_Eats`, `@Uber_Support`, regional handles like `@Uber_UK`).
* **Decision**: Audited outbound tweets (`inbound == False`) across all 2.81M rows. Discovered that the primary, unified brand handle in this corpus is exactly `Uber_Support` (56,270 outbound tweets), making it the 3rd largest brand in the dataset after AmazonHelp and AppleSupport.
* **Why**: Validating the exact handle in code prevents missing customer conversations and confirms Uber has ample sample density while being 3x more computationally tractable than AmazonHelp.

### Decision 3: Selection of `Uber_Support` Over Alternative Brands
* **Context**: The assignment instructs us not to blindly assume Uber is the final choice, but to evaluate whether alternative brands provide higher-quality conversational data for customer-support AI systems.
* **Empirical Comparison Across 2.81M Rows**:

| Brand | Outbound Tweets | Avg Length (chars) | DM Deflection Rate (%) | Help URL Rate (%) | Multi-Turn Follow-up (%) | Core Limitation / Quality Assessment |
|---|---|---|---|---|---|---|
| **AmazonHelp** | 169,840 | 124.0 | 0.64% | 41.30% | 50.21% | **High multilingual noise** (Japanese, Spanish, German, French mixed under one handle); massive product domain. |
| **AppleSupport** | 106,860 | 136.6 | 52.47% | 75.35% | 29.54% | **Severe DM deflection** (>52% boilerplate redirects); repetitive OS/hardware diagnostics. |
| **Uber_Support** | **56,270** | **110.1** | **35.16%** | **51.28%** | **32.05%** | **Goldilocks choice**: Clean English dialogues, distinct ride-hailing taxonomy, balanced auto-handle vs. escalation. |
| **SpotifyCares** | 43,265 | 129.6 | 30.79% | 50.49% | 31.86% | **Low escalation diversity**: Almost exclusively app/cache troubleshooting with minimal safety/financial risk. |
| **Delta** | 42,253 | 103.9 | 16.45% | 15.34% | 28.43% | **Heavy live operational API dependency** (PNR lookups, airport gate changes, real-time flight delays). |

* **Decision**: Formally selected `Uber_Support` as the project's target brand.
* **Why**: 
  1. *Clean Domain Taxonomy*: Ride-hailing cleanly decomposes into non-overlapping intents (fares, cancellations, lost items, driver conduct, pickup issues).
  2. *Realistic Escalation Boundary*: Uber provides a clear distinction between policy-backed auto-handleable queries (lost item procedures, cancellation fee waiver rules) and mandatory human escalations (physical safety incidents, account takeover, fraudulent charges).
  3. *English-First Focus*: Avoids the complex language-filtering required for AmazonHelp.
  4. *Computational Feasibility*: 56k outbound tweets provides thousands of reconstructable conversations while keeping retrieval latency and evaluation runs under 15 minutes.
* **Alternatives Considered**: 
  - *SpotifyCares*: Best runner-up, but rejected because app bugs rarely present meaningful escalation decisions.
  - *AmazonHelp & AppleSupport*: Rejected due to multilingual fragmentation and excessive boilerplate deflection respectively.

### Decision 4: Graph-Aware Two-Pass Extraction for Bidirectional Context
* **Context**: Filtering only rows where `author_id == 'Uber_Support'` yields 56,270 outbound tweets, but completely drops the customer queries that provoked them. Conversely, filtering text for `@Uber_Support` misses follow-up conversation turns where users drop the handle.
* **Decision**: Implemented a two-pass graph-closure extraction:
  1. *Pass 1 (ID Indexing)*: Mapped all Uber tweet IDs, their parent customer tweets (`in_response_to_tweet_id`), their child customer follow-ups (`response_tweet_id`), and direct inbound mentions of `@Uber_Support` (identifying 125,803 candidate IDs).
  2. *Pass 2 (Metadata Extraction)*: Extracted full records for all 125,528 matched rows to `data/processed/uber_tweets.csv`.
* **Why**: Preserves 100% of the conversational graph, resulting in 42,607 complete, bidirectional customer-agent interaction threads while reducing file size from 492.6 MB to 21.86 MB (a 95.6% reduction).
* **Alternatives Considered**: 
  - *Single-pass regex on `@Uber_Support`*: Rejected because subsequent multi-turn replies frequently omit `@Uber_Support`, truncating conversations.
  - *Extracting only 1-turn Q&A pairs*: Rejected because multi-turn follow-ups are needed to understand whether an issue was actually resolved or escalated historically.

### Decision 5: Conversation Unit Representation & Dual-Text Normalization
* **Context**: Customer tweets contain raw Twitter noise: leading handle mentions (`@Uber_Support @105836`), HTML entities (`&amp;`), and volatile shortlinks (`https://t.co/...`). Feeding raw Twitter handles into TF-IDF models or embedding transformers pollutes vector representations with high-frequency arbitrary ID numbers.
* **Decision**: Designed a structured conversation JSON schema that stores both:
  1. `text`: The raw, immutable tweet string (ensuring auditability and exact reference).
  2. `text_clean`: Normalized text with unescaped HTML, stripped leading `@mentions`, and standardized `[URL]` tokens.
  Conversations are structured as chronological sequences from the initial customer inquiry through all intermediate agent replies and follow-ups, capped at 6 turns.
* **Why**: Allows classifiers and retrieval models to focus purely on customer intent semantics (e.g. *"Driver charged me twice for toll"*) while preserving original tweets for full auditing.
* **Alternatives Considered**: 
  - *In-place destructive text cleaning*: Rejected because losing original tweet IDs or URLs prevents verifying ground-truth link citations.
  - *Treating every tweet independently*: Rejected because single tweets lack conversational context (e.g., customer saying *"Yes, that was the one"* makes no sense without the preceding Uber question).

### Decision 6: Pruning Low-Signal / Pure-Mention Inquiries
* **Context**: During conversation reconstruction, we identified 145 threads where the customer's initial tweet consisted purely of `@Uber_Support` or `@115877 @Uber_Support` with zero descriptive text (e.g., tagging the brand in a photo or trying to get attention).
* **Decision**: Formulated an explicit data quality filter discarding conversations where `first_customer_query_clean` is empty.
* **Why**: Tweets with zero semantic content cannot be classified into any intent taxonomy and would degrade evaluation benchmark reliability and classifier training.
* **Alternatives Considered**: 
  - *Creating a "Greeting/Empty" intent*: Rejected because customer support agents cannot take action or auto-handle a message containing only a brand tag with no issue stated.

### Decision 7: Formulating a Compact 6-Intent Taxonomy Over Fine-Grained Classes
* **Context**: Customer support datasets can be split into dozens of hyper-specific micro-intents (e.g., *"lost iPhone"*, *"lost keys"*, *"cleaning fee"*, *"toll fee"*, *"vomit fraud"*). However, overly granular taxonomies suffer from high inter-annotator disagreement, blurred decision boundaries, and poor classifier generalization.
* **Decision**: Synthesized 6 mutually exclusive, operationally actionable intents grounded in empirical TF-IDF/K-Means clustering:
  1. `cancellation_issue`
  2. `fare_and_payment_dispute`
  3. `lost_item`
  4. `driver_conduct_and_safety`
  5. `pickup_and_route_issue`
  6. `account_and_promo_issue`
* **Why**: Every intent in this taxonomy maps directly to distinct business actions and escalation rules, maintaining high classification reliability and clear evaluation rubrics.
* **Alternatives Considered**: 
  - *Merging down to 3 coarse classes (Billing, Ride, Account)*: Rejected because it groups safe auto-handled queries (lost items) with mandatory safety escalations (reckless driving).
  - *15+ granular classes*: Rejected due to high label ambiguity and severe data sparsity on minority classes.

### Decision 8: Deterministic Multi-Intent Precedence Hierarchy
* **Context**: Customer messages often contain overlapping complaints (e.g., *"Driver was rude, cancelled the ride, and charged me $5"*).
* **Decision**: Established a single-label classification framework enforced by a strict priority hierarchy:
  `Safety / Threat` > `Lost Item` > `Cancellation Issue` > `Fare Dispute` > `Route/Pickup` > `Account/Promo`.
* **Why**: Prioritizes passenger safety and urgent personal property recovery above transactional disputes. Avoids the computational complexity of multi-label classification while guaranteeing safety-first arbitration.
* **Alternatives Considered**: 
  - *Multi-label classification*: Considered, but the assignment explicitly specifies classifying into a small set of intents. Introducing multi-label evaluation would complicate metric interpretation without improving escalation safety.

### Decision 9: Adding a 7th `out_of_scope_or_unclear` Intent and Re-Running Discovery on the Full Query Pool
* **Context**: A handoff audit found that the original Step 4 write-up claimed the 6-intent taxonomy was "derived via TF-IDF n-gram extraction and K-Means clustering," but the actual `intent_discovery_report.json` (k=6, a random 20,000-query subsample of the 42,186 available) told a different story: 47.1% of the clustered sample was noise/gibberish, 11.7% was Uber Eats food-delivery content with no matching intent, and neither `driver_conduct_and_safety` nor `pickup_and_route_issue` appeared as a distinct cluster at all.
* **Investigation**: Re-ran clustering on the full 42,186-query pool at k=8, 10, and 12 to see whether more data and finer granularity would surface cleaner structure. At k=10 on the full pool: fare/cancellation, lost-item, account/security ("disabled"/"hacked"), a pickup-wait cluster ("minutes away", "waiting"), and Uber Eats content all separate out distinctly, while a large diffuse cluster (41.65%) remains — vocabulary-generic messages ("uber", "ride", "driver", "url") that don't cleanly split further under bag-of-words TF-IDF. `driver_conduct_and_safety` and `pickup_and_route_issue` still don't form their own top-level clusters; they're real but comparatively rare, and their signal sits inside the large generic cluster and the driver-focused clusters rather than being separable by frequency alone.
* **Decision**:
  1. Made `discover_intents.py` cluster the full query pool by default (`sample_size=None`) instead of a 20k subsample, and raised `num_clusters` from 6 to 10, since both changes produced measurably cleaner, more interpretable clusters without materially increasing runtime (still well under a minute).
  2. Added a 7th taxonomy label, `out_of_scope_or_unclear`, covering two things that are now directly visible as distinct clusters and were previously being forced into one of the six ride intents or left unaccounted for: (a) Uber Eats / food-delivery content — a different Uber business line this taxonomy doesn't model policy for — and (b) generic, low-signal messages with no stated problem. Its escalation policy is `mandatory_escalate`: a human should redirect Eats traffic or ask a clarifying question, never guess.
  3. Rewrote the provenance language in `docs/intent_taxonomy.md` to state plainly that clustering *informed* the taxonomy rather than mechanically producing it — the six ride-support intents were finalized by qualitative, domain-informed labelling of cluster content, with the two safety/route intents in particular preserved on domain-knowledge grounds despite not dominating any single cluster.
* **Why**: The original framing overstated the clustering evidence and left ~20% of real traffic (Eats + low-signal) with no legitimate label, which would have forced the Step 5 golden set to either mislabel that traffic or silently exclude it — either way understating how much of the real inbound stream a ride-support classifier will actually see and must safely decline to handle.
* **Effect on prior results**: The 6 original ride-support intents, their definitions, and escalation policies are unchanged. `data/processed/uber_conversations.json` and all Step 1-3 numbers are unaffected. Only `data/audit/intent_discovery_report.json` was regenerated (new clusters, still 6 clusters → 10 clusters), and `taxonomy.py` / `intent_taxonomy.md` / `test_taxonomy.py` were updated to add the 7th intent.
* **Alternatives Considered**:
  - *Leave the 6-intent taxonomy as-is and just fix the misleading README wording*: Rejected — it would still leave Eats and low-signal traffic with no legitimate label, which materially affects how representative the Step 5 golden set can be.
  - *Split Eats and low-signal into two separate intents instead of one combined label*: Considered, but both resolve to the same operational action (mandatory escalate, no ride policy applies), and the assignment favors a small, compact taxonomy — splitting them would add a label without changing any downstream behavior.
  - *Force Eats/noise traffic into the nearest existing ride intent*: Rejected — this is exactly the mislabeling the audit flagged; it would corrupt intent-level precision/recall in the eventual evaluation.

### Decision 10: Floor + Proportional-Top-Up Stratified Sampling for the Golden Set (Not Random, Not Purely Proportional)
* **Context**: The golden set (150-250 examples) needs to both reflect real traffic *and* give every intent, especially rare high-stakes ones (`driver_conduct_and_safety`, `pickup_and_route_issue`), enough support to compute a meaningful per-class F1. Pure random sampling would starve those two intents (estimated ~1-2.5% of frame each); pure proportional sampling has the same problem.
* **Decision**: Used a "floor + proportional top-up" quota (18 examples floor per intent, then 74 remaining slots allocated proportional to estimated real frequency) at n=200, further stratified within each intent bucket by difficulty (easy/multi-intent-ambiguous/short-message/long-conversation, ~50/25/15/10 split). Implemented in `src/evaluation/sample_golden_set.py`, seeded (`random_state=42`) for reproducibility.
* **Why**: Guarantees every intent has ≥21 examples (enough for a per-class F1 to be informative) while still weighting the majority of the budget (fare, out-of-scope, cancellation) toward what real traffic actually looks like, and deliberately oversamples the assignment's required difficulty axes (ambiguous, short, long, multi-intent) rather than leaving them to chance.
* **A pseudo-intent heuristic classifier, not the final label, drives stratification**: a keyword-matching heuristic (superset of `taxonomy.py`'s keyword lists) assigns a provisional `pseudo_intent_heuristic` used only to build balanced candidate pools per intent. Spot-checking confirmed this heuristic has real false negatives (a "$0 bill" fare dispute and a "waited 90 mins" pickup complaint were both heuristically bucketed as `out_of_scope_or_unclear` because they didn't contain a fixed keyword phrase). `gold_intent` is left `null` in the output and must be assigned by a careful hand-labelling pass — see `docs/golden_set_methodology.md`.
* **Leakage handling**: (1) near-duplicate collapse in the sampling frame (dropped 402/42,186 near-identical customer messages before sampling) so the golden set isn't padded with template repeats; (2) a leakage manifest (`data/golden/golden_conversation_ids.json`) reserving all 200 `conversation_id`s, to be excluded from any retrieval corpus built in Step 7 — re-verified at that build time, not just asserted here.
* **Effect on results**: New artifacts only (`data/golden/`); no prior Step 1-4 numbers changed.
* **Alternatives Considered**:
  - *Pure random sampling*: Rejected — would make rare-intent metrics statistically meaningless (see Context).
  - *Pure proportional-to-frequency sampling*: Rejected — same failure mode as random, just slightly less severe; still leaves `pickup_and_route_issue` with ~2 examples at n=200.
  - *Equal quota per intent regardless of real frequency*: Considered, but would make the golden set's overall composition unrepresentative of real inbound traffic, which the report needs to be honest about when interpreting headline numbers (Section 23 of the assignment).

### Decision 11: Hand-Labelling Rules — Eats-Always-Out-of-Scope, Split Escalation Policy for Out-of-Scope, and a Documented Taxonomy Gap
* **Context**: With all 200 candidates hand-labelled (`data/golden/golden_evaluation_set.json`, via `src/evaluation/apply_hand_labels.py`), three consistent judgment rules were needed to label 200 real, messy examples reliably rather than case-by-case improvisation.
* **Decision**:
  1. **Any message whose actual subject is Uber Eats/food delivery is labelled `out_of_scope_or_unclear`, regardless of which ride-intent keyword happened to match it.** E.g. "cancelled my order", "charged for missing food" pattern-match `cancellation_issue`/`fare_and_payment_dispute` keywords but are Eats issues. This was the single largest source of correction versus the sampling heuristic: pseudo-intent vs. hand-label agreement was only 74% (148/200), almost entirely from this exact failure mode.
  2. **Within `out_of_scope_or_unclear`, escalation policy is split by sub-type**: the Eats sub-type always escalates (different business line, no policy grounding); the noise sub-type escalates only when there's a real unresolved concern or insufficient information to act safely — a pure feature request, a safely-answerable informational question, or a joke/boast is labelled `should_escalate = false` (safe to auto-acknowledge). This is a refinement of the uniform `mandatory_escalate` policy set in `taxonomy.py` for this intent: the taxonomy's default policy is a reasonable, conservative *default* for an automated system, but a human labeller applying judgment to each example can tell "no ride policy applies" (Eats — always escalate) apart from "nothing needs solving" (idle chatter — safe to close).
  3. **A driver forcing a passenger out of the vehicle is labelled `driver_conduct_and_safety`, not `pickup_and_route_issue`**, and **an extortion-style "won't return my item unless I pay" claim escalates under `driver_conduct_and_safety`**, both per the taxonomy's own documented boundary rules in `docs/intent_taxonomy.md`.
* **A genuine taxonomy gap was found and documented rather than silently patched**: `golden_0091` (account hacked → fraudulent trip charges) is a case where the fixed precedence hierarchy mechanically resolves to `fare_and_payment_dispute` (rank 4) over `account_and_promo_issue` (rank 6), but the root cause is account takeover, not a billing dispute. Labelled `account_and_promo_issue` by explicit human override, with the conflict recorded in `labeling_notes` for discussion in the Step 10 failure analysis — the precedence hierarchy has no rule for "the higher-precedence intent is a *symptom* of the lower-precedence one," and this is exactly one real example of it, not a hypothetical.
* **Why**: These rules make 200 independent judgment calls reproducible and explainable as one policy instead of 200 ad hoc decisions, and the escalation-policy split for `out_of_scope_or_unclear` avoids a real system needlessly routing harmless chatter to a human queue while still being conservative about anything genuinely out of the agent's grounding.
* **Effect on results**: Gold intent distribution differs meaningfully from the pseudo-intent distribution used for sampling — most notably `out_of_scope_or_unclear` grew from 37 (pseudo) to 58 (gold) as Eats-flavored false negatives in other buckets were corrected. `should_escalate` is 130/200 (65%) True, driven heavily by `out_of_scope_or_unclear` (55/58) and the mandatory-escalate `driver_conduct_and_safety` (21/21) — this is a consequence of the floor+top-up sampling design intentionally over-representing rare/high-stakes intents, and **must not be read as an estimate of real-world escalation volume** (flagged for the "misleading headline number" report section).
* **Alternatives Considered**:
  - *Bulk-fill `should_escalate` from the intent's default policy in `taxonomy.py`*: Rejected — this was flagged as unsafe back in the Step 5 methodology doc precisely because message-level risk (amounts, repetition, prior unresolved contact, personnel demands) changes the correct decision within the same intent.
  - *Silently resolve the golden_0091-style precedence conflict by tweaking `INTENT_PRECEDENCE`*: Rejected — changing the taxonomy's precedence rule specifically because of one example is exactly the kind of silent evaluation-design change Section 31 prohibits; documenting the gap and overriding by hand for this one case is the honest path.
  - *Uniform mandatory-escalate for all of `out_of_scope_or_unclear` (no sub-type split)*: Considered for simplicity, but produces an unrealistic system that escalates harmless chit-chat and feature requests, which would itself be a misleading signal about the agent's practical usefulness.

### Decision 12: Baselines Trained on Heuristic Weak Labels, Not the Golden Set
* **Context**: Step 6 needs two intent-classification baselines (majority-class, TF-IDF+LogReg) evaluated on the frozen golden set. Neither baseline can be trained ON the golden set: it's only 200 examples (too small, and reserved as the rare-intent-stratified test set for the whole project), and no other hand-labelled corpus exists.
* **Decision**: Trained both baselines on the Step 5 heuristic pseudo-intent labels (`src/evaluation/sample_golden_set.py`'s keyword classifier) applied to the ~42k-conversation corpus, explicitly excluding all 200 golden set `conversation_id`s (the leakage manifest). Implemented in `src/classification/baselines.py`.
* **A leakage gap was found and fixed, not just asserted**: the first version of `build_training_set()` only excluded by `conversation_id`. A test (`test_no_golden_conversation_in_training_pool`, quickly followed by a working regression test after a real failure) caught that one training conversation (`conv_1156838`) had **exact-duplicate text** to `golden_0143` under a **different** `conversation_id` — a retweet/duplicate-row artifact in the raw Twitter data. The conversation_id-only leakage manifest missed this by design (documented as a known limitation back in the Step 5 methodology doc's near-duplicate discussion). Fixed by also excluding training rows whose text exactly or near-duplicate-matches (`near_duplicate_signature`) any golden set message, regardless of conversation_id. Only 1 of ~42k rows was affected, but the principle matters for Step 7's much larger retrieval corpus, where duplicate-text leakage is a bigger risk.
* **Why weak-label training is a legitimate choice, with a known ceiling**: Step 5 measured the heuristic's agreement with true gold labels at 74% (148/200). Training on these labels means neither baseline can be expected to exceed roughly that ceiling by intent category — this isn't a flaw to hide, it's exactly the kind of caveat the report's "what's misleading about my headline number" section needs. It's also realistic: this is what you actually do when gold labels are scarce and expensive.
* **Results**: Majority-class (always predicts `out_of_scope_or_unclear`, the largest training bucket): 29% accuracy, 0.0642 macro F1 (0 F1 on 6/7 intents it never predicts — expected, this is the floor). TF-IDF+LogReg: 71% accuracy, 0.7238 macro F1 — a large, genuine improvement despite training on noisy weak labels, though its weakest class is `out_of_scope_or_unclear` itself (0.5631 F1), consistent with that intent carrying the heuristic's own worst label noise.
* **Effect on results**: New artifacts only (`data/results/`); golden set and taxonomy untouched.
* **Alternatives Considered**:
  - *Split the golden set into train/test*: Rejected — would gut the deliberately rare-intent-heavy stratified sample (e.g. `driver_conduct_and_safety` would drop from 21 to ~15 examples on each side), and the assignment wants baselines and the AI system compared on the SAME full evaluation set.
  - *Hand-label a larger training corpus*: Out of scope for a 15-minute-reproducible take-home; 200 hand-labelled examples already took a full careful pass.
  - *Use raw keyword rules directly as a third "baseline" instead of training a model on them*: Considered, but that's just the Step 5 heuristic itself re-reported, not a second distinct baseline family as the assignment asks for (a trivial baseline + a traditional-ML baseline).

### Decision 13: AI Agent Uses Google Gemini (Free Tier), Not the Anthropic API -- and a Single Call Does Classification + Escalation + Drafting Together
* **Context**: Step 7's AI agent needs an LLM for grounded response generation (Section 16 explicitly rules out generic-knowledge-only generation). The project owner has a Claude.ai subscription but no separate Anthropic API billing set up, and the Anthropic API is billed independently of that subscription. Rather than take on API cost, the owner supplied a Google AI Studio (Gemini) free-tier API key and asked to use it instead.
* **Decision**: Built `src/pipeline/support_agent.py` on the `google-genai` SDK. Went through two model changes during live testing, both discovered by calling the real API rather than guessed from training knowledge:
  1. `gemini-2.5-flash` returned a 404 ("no longer available to new users, use gemini-3.6-flash") on the first live call.
  2. `gemini-3.6-flash` turned out to carry a **20 requests/DAY** free-tier cap (not just a per-minute limit) -- discovered only after it started returning `RESOURCE_EXHAUSTED` a handful of calls into the real 200-example run. Switched to `gemini-flash-lite-latest`, which cleared all 200 calls with zero quota failures. The partial `gemini-3.6-flash` cache (11 examples) was discarded rather than mixed in, so the final 200 results all come from one consistent model.
  `thinking_level="low"` is used throughout since this is a bounded classification + short-drafting task, not open-ended reasoning.
* **One LLM call per message does classification, the escalation decision, and response drafting together**, rather than a separate classifier (e.g. reusing the Step 6 TF-IDF+LogReg baseline) feeding a second LLM call. Cheaper and more coherent -- the escalation decision and the draft both reason over the same retrieved evidence in the same pass, instead of a rule layer second-guessing an independent classifier.
* **A live smoke test caught a real prompt bug before the full run**: the schema's `escalation_reason` field is `str`-required, but the model returned the literal string `"None"` when NOT escalating, because the prompt only asked for a reason to justify escalating, not to justify auto-handling. Fixed by explicitly requiring a real justification in both directions in both the prompt and the Pydantic field's inline comment; confirmed fixed with a re-run on the same example, and confirmed again after the full run (0/200 results contain an empty or "None" reason -- see `tests/test_agent_evaluation.py`).
* **A retry-handler bug was caught by the run itself, not silently**: the first version checked `e.status_code` on a `genai_errors.ClientError`, but the SDK's actual attribute is `e.code` -- this crashed the whole run on the very first 429 instead of retrying. Caught immediately because the run was checkpointing to disk after every call (5 examples had already saved), fixed, and resumed from the same cache with zero lost progress.
* **Why Gemini over Anthropic**: Respecting the project owner's explicit cost preference matters more than which LLM vendor is used -- the pipeline's design (retrieval-then-single-structured-call, grounding rules, safety-policy override) is what's actually being evaluated by this assignment, and none of it is Anthropic-specific.
* **Result**: All 200 examples completed cleanly on `gemini-flash-lite-latest` with zero quota failures. **Intent accuracy 87.0%, macro F1 0.8634** -- beats both Step 6 baselines by a wide margin (majority-class 0.0642, TF-IDF+LogReg 0.7238 macro F1). **Escalation accuracy 76.0%** (F1 0.8125 on the escalate=True class, 0.6667 on escalate=False) -- meaningfully weaker than intent classification, and the honest reading is that the agent over-escalates: it catches true escalations well (recall 0.80) but wrongly escalates roughly 31% of messages that should have been auto-handled (escalate=False recall only 0.6857). This asymmetry is safety-conservative (errs toward a human, not toward an unsupervised wrong answer) but is a real accuracy gap to discuss honestly in the Step 10 failure analysis, not smooth over. `driver_conduct_and_safety` escalated 21/21 (100%) via the model's own reasoning -- the code-level defensive override never had to fire.
* **Effect on prior results**: None. `requirements.txt` swapped `anthropic` for `google-genai` + `pydantic`; `.env` (gitignored) holds `GOOGLE_API_KEY`. New outputs only: `data/results/ai_agent_results.json`, `ai_agent_metrics.json`, `system_comparison.json`.
* **Alternatives Considered**:
  - *Retrieval-only response generation (no LLM call at all)*: Offered to the user as a zero-cost fallback before the Gemini key was provided; superseded once a working free-tier key was available, since a real generative step is closer to the assignment's intended architecture (Section 16) than pure lookup.
  - *Paid Anthropic API*: Rejected by the project owner on cost grounds given the free Gemini alternative was available and proved sufficient for this project's scale.
  - *Spreading the `gemini-3.6-flash` run across ~10 days to respect its 20/day cap*: Rejected in favor of switching to the lite model, which completed the full run in one pass with no quality loss observed on spot checks.
  - *Separate classifier + separate drafting call*: Rejected -- doubles call volume for no accuracy benefit here, and risks the drafting call disagreeing with the classifier's own intent.

### Decision 14: One Diagnosed, Documented Prompt Revision to Fix Escalation Accuracy (76.0% -> 85.0%) -- Not Iterative Tuning Against the Golden Set
* **Context**: Decision 13's initial run scored 87.0% intent accuracy / 0.8634 macro F1 (clearly beating both baselines) but only 76.0% escalation accuracy -- a real, separate weakness worth investigating on its own, not glossed over just because the headline intent number looked good.
* **Diagnosis before any fix (Section 34 discipline)**: read every one of the 22 over-escalations (false positives) and 26 under-escalations (false negatives) in `data/results/ai_agent_results_v1_baseline.json`. Two clear, distinct root causes, not noise:
  1. **Over-escalation**: the model was treating "this needs someone to check an account/trip record" as grounds to escalate -- but for this taxonomy, giving the standard self-serve redirect link (what real Uber support actually does, per the retrieved historical evidence) IS the correct AUTO-HANDLE outcome; escalation is supposed to be reserved for specific named triggers, not general "a human will eventually be involved somewhere down the line" reasoning. The original prompt's escalation criteria were prose, not a checklist, and left this distinction implicit.
  2. **Under-escalation**: several genuine escalation triggers that the gold labels applied consistently (repeated/pattern language like "3 times"/"5 months"/"multiple times", explicit unauthorized-charge language, an explicit request for a human, a circular self-service lockout) were already implied by `ESCALATION_POLICIES`' prose `policy_rationale` text in the prompt, but not called out explicitly enough for the model to weight them reliably. Separately, one specific miss (`golden_0142`) traced to a real documentation gap: `docs/intent_taxonomy.md` has boundary-case prose ("a driver forcing a passenger out of the vehicle is `driver_conduct_and_safety`, even framed as a fare dispute") that was never captured in `taxonomy.py`'s machine-readable `INTENT_DEFINITIONS` -- so the agent's system prompt (built from `taxonomy.py`, not the markdown doc) never saw it.
* **Decision**: One revision, informed by that diagnosis, not iterative hillclimbing against the golden set:
  1. Rewrote the AUTO-HANDLE vs. ESCALATE section of `build_system_prompt()` in `src/pipeline/support_agent.py` to (a) explicitly define what "auto-handle" means operationally in this business (give the standard redirect; that's a complete, correct outcome; a human processing the backend case afterward doesn't make it an escalation), and (b) replace the prose escalation criteria with an explicit lettered checklist (a)-(h) of the *only* valid triggers, requiring the model to name which one applied (or state that none did) in `escalation_reason`.
  2. Added a `boundary_notes` field to `INTENT_DEFINITIONS` in `taxonomy.py` for the two intents with a real documented-but-unwired boundary rule (`lost_item`'s extortion-escalates-under-safety, `driver_conduct_and_safety`'s forced-exit rule), and wired it into the prompt -- this closes a docs/code inconsistency, it doesn't invent new policy.
  3. Regenerated all 200 results in one pass (`data/results/ai_agent_results.json`), preserving the pre-fix run as `ai_agent_results_v1_baseline.json` / `ai_agent_metrics_v1_baseline.json` for an honest, auditable before/after rather than overwriting the evidence.
* **Result**: Escalation accuracy 76.0% -> **85.0%**; escalate=True F1 0.8125 -> **0.877** (precision 0.8254 -> 0.9386, recall 0.80 -> 0.8231). Raw counts: false positives (over-escalation) 22 -> **7** (-68%); false negatives (under-escalation, the more dangerous direction) 26 -> **23** (-12%). Both error directions improved together -- this was not a threshold trade-off in one direction at the other's expense. Intent classification was essentially unchanged (87.0% accuracy both runs; macro F1 0.8634 -> 0.8628, noise-level), confirming the fix targeted escalation reasoning specifically rather than generally perturbing the model. `golden_0142` (the case that motivated the boundary-notes fix) now classifies and escalates correctly, citing the boundary rule by name in its own reasoning.
* **Why this doesn't compromise evaluation integrity**: the golden set's labels, schema, and composition were never touched (Section 31). What changed is the SYSTEM being evaluated, based on a qualitative failure-mode diagnosis of *why* it was wrong -- the same kind of iteration any ML system goes through before it's considered "done," and explicitly permitted (expected, even) by Section 22's failure-analysis requirement. The discipline that keeps this from becoming score-chasing: one diagnosis pass, one revision, one re-run, both versions kept on disk and reported honestly -- not a loop of small tweaks re-run against the same 200 examples until the number looks good.
* **Effect on prior results**: Step 6 baselines, golden set, and taxonomy intent definitions unchanged (only the new `boundary_notes` field was added, additive). `data/results/ai_agent_results.json`, `ai_agent_metrics.json`, `system_comparison.json` now reflect the v2 (post-fix) run; v1 preserved under `*_v1_baseline.json` for the record.
* **Alternatives Considered**:
  - *Raise `thinking_level` from "low" to "medium"/"high" instead of rewriting the prompt*: Considered, but the diagnosis pointed to a specific missing checklist/definition, not insufficient deliberation -- fixing the actual instruction gap is more targeted and doesn't cost extra tokens/quota on every future call.
  - *Iteratively tune the prompt across several more rounds to push the number higher*: Rejected -- diminishing, riskier returns, and repeated tuning against the same 200-example frozen set starts to blur into overfitting the eval rather than improving the system, which is exactly what Section 29 warns against.
  - *Leave escalation accuracy at 76% and note it as a known limitation for Step 10*: Considered and still valid as a fallback framing, but a concrete, diagnosed, well-understood root cause was already in hand, so fixing it now (once, transparently) was more useful than deferring a fix we already knew how to make.

### Decision 15: Evaluation Harness Regenerates Baselines but NOT the AI Agent by Default
* **Context**: Step 8 needed one command (`evaluate.py`, matching the assignment's own suggested entrypoint name) that reproduces the project's headline results, honoring the README's "under 15 minutes" promise. But the three systems being compared have very different regeneration costs: baselines are free/local/~1 minute; the AI agent needs a `GOOGLE_API_KEY` and, per Decision 13, can take 15-20+ minutes on a free-tier quota.
* **Decision**: `evaluate.py` / `src/evaluation/eval_harness.py` always regenerates the two baselines fresh (cheap, deterministic, and confirms they aren't stale) but only *scores* the AI agent's already-committed `data/results/ai_agent_results.json` against the golden set by default -- it does not re-call the LLM unless `--regenerate-agent` is explicitly passed. If the committed results file is missing entirely (e.g. a clean checkout that somehow dropped `data/results/`), the harness fails fast with an explicit instruction rather than silently trying to make paid/slow API calls on Hiver's behalf.
* **Why**: The assignment explicitly warns against processing being blocked on infrastructure a grader may not have (Section 25/26), and an API key is exactly that kind of dependency. Regenerating baselines every run (rather than trusting a cached file) costs nothing and catches any drift; regenerating the agent every run would make the "15 minute" promise depend on a third party's free-tier rate limits, which is not something this project controls.
* **Effect on results**: New artifacts only -- `evaluate.py`, `data/results/evaluation_report.json` / `.md`. No prior metrics changed; the harness only aggregates and re-presents them.
* **Alternatives Considered**:
  - *Always regenerate everything, including the agent*: Rejected -- ties reproducibility to Gemini's free-tier availability/quota on the day someone runs it, which is outside this project's control and contradicts the explicit 15-minute target.
  - *Never regenerate anything, always read cached files*: Rejected for the baselines specifically -- they're free and fast enough that confirming them live is strictly better than trusting a file that could go stale silently.
  - *A single monolithic script instead of a thin harness over existing per-step scripts*: Rejected -- Steps 6/7's scripts are already tested independently; the harness's job is orchestration and reporting, not re-implementing metric logic a second time.

### Decision 16: Response-Quality Rubric Design, Human-Rater Identity, and Choosing MAD Over Spearman/Kappa as the Primary Agreement Statistic
* **Context**: Step 9 needed (1) a versioned 6-dimension rubric matching Section 20 exactly (correctness, groundedness, helpfulness, safety, brand_consistency, tone), (2) a human-rated subset in the 40-60 range (Section 21) to calibrate an LLM judge against, and (3) an honestly-chosen agreement statistic rather than one picked because it looks good.
* **Rubric**: 1-5 scale per dimension, defined once in `src/evaluation/rubric.py` (v1.0) and rendered identically into both the LLM judge's prompt and the human-rating reference doc (`docs/response_quality_rubric.md`) -- a single source of truth, since an agreement comparison between two raters using subtly different criteria would be meaningless.
* **Human-rater identity, stated plainly**: as in Step 5, the "human" rater is the developer/agent who built the system -- no separate annotator pool was available. This is documented as a limitation in `docs/response_quality_rubric.md` itself, not just in a report footnote: single-rater self-calibration is not equivalent evidentiary weight to inter-rater reliability across a diverse human pool, and shares some risk of correlated bias with the system's own design assumptions.
* **Subset sampling**: n=50 (`src/evaluation/sample_judge_subset.py`), stratified proportionally to the golden set's own `gold_intent` distribution -- subsampling an already-deliberately-stratified sample preserves its design rather than introducing new, uncontrolled bias. Rated BEFORE running the LLM judge on those examples, to avoid anchoring on the judge's own scores while rating.
* **A live smoke test caught a real SDK issue before the full run**: `Literal[1, 2, 3, 4, 5]` as a Pydantic field type produces an integer enum that `google-genai`'s schema converter cannot translate (it expects string enums), raising 30 validation errors on the first call. Fixed by using `int = Field(ge=1, le=5)` instead -- caught by testing against the real API before committing to 200 calls, not discovered mid-run.
* **A live smoke test also validated the judge isn't rubber-stamping**: before running all 200, the judge was tested specifically against 4 examples the human pass had scored low (including `golden_0100`, where the draft response copied a customer name, "Annabel", from the retrieved evidence into a reply for a different customer). The judge independently caught the same issue, in one case scoring it even lower (groundedness 1 vs. the human's 2) -- evidence the judge is actually discriminating, not defaulting to high scores.
* **Choosing the primary agreement statistic AFTER seeing the data, not before**: computed all three candidates (MAD, Spearman r, weighted Cohen's kappa) per dimension and pooled. `safety` and `brand_consistency` have very low score variance (both rater and judge cluster near 5 on almost every example), which makes their Spearman r (safety: -0.082) and kappa (safety: -0.068) statistically unstable and, read in isolation, misleadingly suggest active disagreement -- while `safety`'s MAD is actually the LOWEST of all six dimensions (0.22), meaning the two raters are in fact the closest to each other there. This is exactly the "don't pick a statistic that hides what the data is doing" problem Section 21 warns about. **Decision: report all three for every dimension, but treat Mean Absolute Disagreement as the primary/headline statistic**, since it stays well-defined and interpretable regardless of a dimension's score variance, while Spearman/kappa are reported as secondary context specifically flagged as unreliable on low-variance dimensions.
* **Result**: Pooled across all 300 (dimension, example) score pairs -- MAD 0.67 (typically well under 1 point apart on a 5-point scale), Spearman r 0.436 (moderate, p<0.001), weighted kappa 0.385 (fair-to-moderate), exact match rate 46%, within-1-point rate 87.3%. `groundedness` has the strongest agreement by kappa (0.483); `safety` has the lowest raw disagreement (MAD 0.22) but the least reliable correlation-based stats due to low variance; `tone` -- the most inherently subjective dimension -- has the weakest agreement (kappa 0.209). This is reported as a moderate, honest agreement level, not oversold as strong.
* **Effect on prior results**: None. New artifacts only: `src/evaluation/rubric.py`, `sample_judge_subset.py`, `llm_judge.py`, `judge_agreement.py`; `docs/response_quality_rubric.md`; `data/judge/`.
* **Alternatives Considered**:
  - *Pick Spearman correlation as the sole headline statistic (common in many eval writeups)*: Rejected -- would have reported `safety`'s -0.082 at face value, actively misleading about a dimension where the two raters actually agree closely in raw terms.
  - *Only report kappa*: Rejected for the same low-variance instability reason, plus kappa's stricter chance-correction can look artificially low on a 5-point scale with few examples even when raw agreement is decent.
  - *Use a 1-3 or 1-10 scale instead of 1-5*: Rejected -- 1-3 loses real distinctions observed while scoring (e.g. "generic but safe" vs. "actively unhelpful" both being 1); 1-10 implies a precision neither a human skimming 50 examples nor an LLM judge can reliably deliver.

### Decision 17: Failure Mode Selection Prioritized Diversity and a Metrics-Blind-Spot Finding Over the "Biggest Number" Failures
* **Context**: Section 22 asks for the top 5 failure modes with real examples, each including expected/actual behavior, root cause, hypothesis, and a potential improvement. With 200 scored examples across intent, escalation, and 6 response-quality dimensions, there were far more than 5 candidate patterns to choose from.
* **Decision**: Selected for diversity across the pipeline (data quality, intent classification, escalation logic, response generation) rather than picking the 5 numerically largest error buckets, which would have clustered around similar themes (e.g. several different framings of "Eats vs. ride confusion"). `reports/failure_analysis.md`'s five modes: (1) escalated-response phrasing ungrounded in evidence (a direct, traceable side effect of the Decision 14 fix -- 7.0% of escalated responses vs. 0% of auto-handled ones), (2) cross-customer detail leakage (`golden_0100`'s "Annabel" -- rare but high-severity), (3) "redirect reflex" on directly-answerable questions, (4) intent misclassification toward `driver_conduct_and_safety` overstating response severity while both intent-accuracy and escalation-accuracy metrics stay blind to it, (5) the Step 5/6 weak-label training ceiling.
* **Failure mode 4 is the most methodologically important one**: `golden_0049` and `golden_0159` both have wrong predicted intent AND a resulting inappropriately severe response, yet `should_escalate` still matches gold in both cases (coincidentally -- `driver_conduct_and_safety` is mandatory-escalate, and both gold intents also happened to be escalate=True). Neither the 87.0% intent accuracy nor the 85.0% escalation accuracy headline number flags either example as wrong. Only the response-quality judge caught it. This is documented explicitly as a real "what's misleading about my headline number" example with a name and a number, not a hypothetical caveat.
* **Every cited number is regression-tested**, not just written down: `tests/test_failure_analysis.py` recomputes each claim (the 8/114 vs. 0/86 groundedness split, the specific cited examples' properties, the 74.0%/148 heuristic-agreement figure) directly from the underlying result files, so if a future rerun changes the data, the report's specific numbers get caught as stale by CI rather than silently drifting from the artifacts they describe.
* **Effect on prior results**: None -- this step only analyzes existing artifacts (`data/results/`, `data/judge/`, `data/golden/`) and writes `reports/failure_analysis.md`.
* **Alternatives Considered**:
  - *Report the 5 failure modes with the largest raw counts*: Rejected -- would have produced heavy overlap (several near-duplicate framings of Eats/ride confusion) and missed the metrics-blind-spot finding (mode 4), which has a small raw count (2 confirmed examples) but is arguably the most important insight in the whole analysis.
  - *Only report failure modes visible in the intent/escalation metrics*: Rejected -- would have missed all of the response-quality-specific findings (modes 1-3), which only the Step 9 judge scores surfaced.
  - *Leave the specific counts as prose without a regression test*: Rejected -- a written report's numbers silently going stale after a future data change (e.g. a rerun of the agent or judge) is exactly the kind of drift this project's testing discipline has caught before (Decision 12's leakage bug); the same discipline applies to report claims, not just code behavior.

### Decision 18: The Final Report Leads With a Safety Miss the Headline Metrics Don't Show, Not With the Best-Looking Number
* **Context**: Writing Section 6 ("what's misleading about my headline number") of the final report required going beyond restating already-known caveats (weak-label ceiling, non-representative golden set escalation rate) and actually looking for what the 87.0%/85.0% headline numbers might be hiding.
* **Investigation**: Broke down `driver_conduct_and_safety`'s per-class metrics (precision 0.75, recall 0.857 -- the lowest precision of any intent) and then checked, example by example, what happens to the 3 true safety cases the agent's intent classification misses. 2 of 3 still get escalated anyway, because their fallback intent coincidentally also triggers escalation. The third, `golden_0136` -- a message that literally says "Felt unsafe to give [my destination] over phone" -- was misclassified as `cancellation_issue` and NOT escalated at all.
* **Decision**: Made this the lead finding of Section 6 and the report's callout in `README.md`, ahead of the golden-set-representativeness and weak-label-ceiling caveats that were already documented from earlier steps. Added `tests/test_final_report.py` to lock in the exact breakdown (18 correctly escalated by correct intent, 2 more escalated by coincidence, 1 missed entirely) so this finding can't silently drift if the agent or judge is ever re-run.
* **Why**: A 1-in-200 (0.5%) failure rate is exactly the kind of thing an aggregate accuracy or macro F1 number is structurally unable to surface, and it happens to be the single highest-consequence failure type this project could produce (a real safety report going unescalated). Reporting it prominently, with the specific example and a concrete proposed fix (§7 of the final report: a safety-language second-pass check independent of primary intent classification), is a more honest and more useful headline-number critique than a purely statistical one.
* **Effect on prior results**: None -- this is an analysis of existing artifacts, not a code or data change. Failure Mode 4 in `reports/failure_analysis.md` (Decision 17) already documented the *pattern* of intent-driven severity/escalation mismatches using two other examples (`golden_0049`, `golden_0159`); this decision extracts the specific, more severe instance of that same pattern and elevates it as the report's headline caveat rather than leaving it embedded as one bullet among several.
* **Alternatives Considered**:
  - *Lead Section 6 with the golden-set-representativeness caveat (65% escalate rate vs. real traffic) since it's a bigger, more statistically obvious effect*: Rejected -- true, and still reported, but it's a benchmark-design caveat, not a system-safety one; burying the safety miss beneath it would misprioritize what a reader should worry about most.
  - *Omit the specific example and only report the aggregate precision/recall numbers*: Rejected -- an aggregate 0.75 precision / 0.857 recall doesn't convey that the failure mode includes a real, concrete instance of a stated-unsafe message going unescalated; the example is what makes the caveat actionable rather than abstract.
